# Repo Conventions: Agents

This repository is a collection of self-contained Claude Code agents. This file applies to
the repo as a whole — it is **not** an agent persona. An agent's persona lives in
`agents/<agent-name>/CLAUDE.md` and loads when a session starts in that folder.

## Core Principles

1. **One agent = one folder.** Everything an agent needs lives under
   `agents/<agent-name>/`. No agent reads files from another agent's folder.
   **Exception:** The `consulting-agent` is a generator — it reads and changes other package
   folders when it creates or refactors a package. The packages themselves never depend on each
   other.
2. **Pickability.** Every agent must be adoptable into a foreign repo by copying its folder
   (plus its documented skills). If a change breaks this property, it's wrong.
3. **Markdown and JSON only.** No build steps, no runtime dependencies, no
   installation.
4. **Local only — with one named exception.** The work itself happens on the user's machine: no
   web research, no external services for the actual task. Git remote operations and opening a
   pull request are the exception. They stay **optional**, so principle 3 holds: an agent checks
   whether `gh` and a GitHub remote are present and falls back to a pull request message on disk
   if they are not. `gh` is a bonus, never a requirement.
5. **Shared skills live at the root.** Everything under `.claude/skills/` is available to all
   agents in this repo. An agent that needs a skill names it in its README under
   *Dependencies* — otherwise it gets lost when picked.
   **Exception:** Packages generated by the `consulting-agent` bring their skills along as a
   copy under `agents/<package-name>/.claude/skills/`, so a single copy operation is enough
   to pick them.

## Requirements for a New Agent

A folder under `agents/` is only complete once it contains:

| File | Content |
| --- | --- |
| `CLAUDE.md` | Persona, responsibility, inputs, outputs, communication, specialized grill-me focus |
| `README.md` | What the agent is for, how to start it, which skills it needs |
| `docs/` | Optional: origin context and design decisions |

Afterward: add an entry to the agent table in [`README.md`](README.md).

## Handling Generated Agents

The [`consulting-agent`](agents/consulting-agent/) produces finished packages — a single
agent or a whole orchestra. Such a package lives as **one** folder under `agents/`
and has the same shape as a hand-written agent, extended by its roles:

```
agents/<package-name>/
├── CLAUDE.md
├── README.md
├── .claude/
│   ├── agents/            # the subagents, with model: in the frontmatter
│   └── skills/            # bundled skills, so a single copy operation is enough
└── docs/
```

The package `CLAUDE.md` is the main agent (orchestrator); `.claude/agents/` holds subagents only,
because a subagent can neither talk to the user nor call other subagents. The roles communicate via
delegation (Agent tool), not via files.

**Note:** Hand-written agents may also have a `.claude/` directory with their own
subagents and a `settings.json` — pickability is preserved because everything lives in the
agent folder and is carried along when copied.

## Way of Working

- **Language:** English in documentation and agent definitions. Technical terms and
  identifiers stay in their original form.
- **Test-Driven Development**, whenever code is actually produced (Red → Green).
- **Commits** in English, imperative, prefixed with the affected agent's name,
  e.g. `consulting-agent: extend grill-me phase with escalation paths`.
- **A branch before the first change, a pull request at the end.** Nothing is written on a main
  branch. Agents commit per phase, open a pull request and stop there — the merge is the user's.
  Review remarks come back as an additional commit on the same branch, never as rewritten history.
  This is where review happens: the user reads the whole change as one diff, not one write at a
  time. That is also why agents leave Plan mode for **auto mode** rather than confirming each
  file individually.
